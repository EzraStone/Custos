§ 01

What Custos is

AI agents are becoming autonomous identities. They hold credentials, call tools, and write to production systems without a human reading each action. Identity and access systems decide which agents may act. Nobody decides which actions are permitted — and at most companies, nobody can say which agents are acting at all.

CrowdStrike made endpoints visible and governable. Custos does that for autonomous agents.

Custos has two halves. The Register discovers agents running in a company's cloud — including the ones nobody enrolled — and maps each to its owner, its credentials, and the systems it can reach. The Checkpoint sits in front of consequential agent actions, verifies cryptographically which agent under whose delegation is proposing them, evaluates them against deterministic policy, and allows, blocks, or routes to a human — issuing a signed receipt either way.

Precision on claims

Two things Custos does not do, stated here so they are never claimed in a deck or a sales call. Custos does not judge whether an action is safe in any semantic sense; it evaluates actions against deterministic policy the customer authored. And the Checkpoint does not detect compromised agents; it gates all actions in its path and evaluates each. Behavioural detection is a Register capability (§4.6), not a Checkpoint one.

§ 02

Why both halves exist

Neither half is viable alone, and the dependency runs in one direction only.

Enforcement without discovery has an empty register. A checkpoint can only govern agents that were enrolled, and the agents that were enrolled are precisely the ones that were already known, reviewed, and least likely to be the problem. Onboarding becomes a manual enumeration exercise the customer cannot complete, because the thing being asked for — a list of every agent they run — is the thing they lack.

Discovery without enforcement is a report read once and filed. It creates awareness and no control, and awareness alone does not renew a contract.

The Register populates the tables the Checkpoint governs. Build the register first; sell the checkpoint to the customers whose findings alarmed them.

Sequencing consequence

The Register ships first — not because it is the better product, but because it is the only half that produces evidence before it is complete. It delivers its most persuasive artifact on day one with no integration, no risk, and no trust required. The Checkpoint's first customer arrives only after the hard part is done.

Microsoft Agent 365 shipped an agent registry, generally available May 2026. It provides a unified tenant inventory including third-party agents. This is the discovery wedge, shipped by the largest possible incumbent.

The scope distinction Custos depends on: Agent 365 sees agents operating in the Microsoft tenant. Custos sees agents operating in cloud infrastructure — services in AWS accounts making model API calls under IAM roles, which the tenant registry has no visibility into. Reporting also suggests Agent 365 is currently more visibility plane than control plane, with enforcement for non-Microsoft agents still maturing.

The honest competitive position

The space is crowded and consolidating — Snyk/Invariant, Coralogix/Aporia, ClickHouse/Langfuse, Anthropic/Humanloop. That validates the category and compresses the window. Never claim the space is empty. Claim one unserved job: which agents are running that nobody enrolled, and what can each one destroy.

§ 04

Phase A — The Register

4.1 The load-bearing technical assumption

Everything downstream depends on one claim that has not been tested:

An agent is distinguishable from a chatbot backend using network and identity metadata alone.

Both make TLS calls to the same model endpoints. Payloads are encrypted and, by design (SEC-18), never inspected. So the classifier must separate them on observable metadata only.

SignalSourceStrength
Burst of sequential model calls, monotonically growing payload size, sub-second gapsFlow log timing + byte countsStrong
No correlated inbound human request in the windowALB / API gateway log correlationStrong
MCP protocol trafficPort and protocol fingerprintStrong
Machine principal rather than user sessionCloudTrailModerate
Call volume inconsistent with human pacingTemporal analysisModerate
Sustained off-hours activityTemporal analysisWeak

The dominant signal is the first: an agent produces bursts of sequential calls with growing context and no inbound human request; a chatbot produces one or two calls tightly coupled to an arriving request. This is inferable without reading a single payload byte, which is what makes the privacy posture in §7 possible rather than aspirational.

Gate G0 — two weeks, ~30 hours

Build a test environment with three agents (a LangGraph service, a coding agent, a tool-calling loop) and two chatbot backends. Capture flow logs and CloudTrail only. Hand-analyse for separation.

Pass → proceed as specified. Fail → fall back to gateway-log ingestion, which requires the customer to already run an LLM gateway. That is a materially weaker wedge and the pitch, timeline, and target profile all change. Decide by end of week 2 either way; do not proceed on hope.

4.3 Collector

  • Deployed by a single CloudFormation or Terraform apply into the customer account. Target: under 30 minutes from a one-page doc, by a platform engineer, without a meeting.
  • Assumes a cross-account role with read-only permissions and no write permission anywhere.
  • Emits derived metadata only. Constructed so that transmitting payload bodies is impossible, not merely disabled — security teams will read the source.
  • Open source (§10, decision 5). It is the component under the most scrutiny and the largest single objection remover in security review.
  • Single static Go binary. Low footprint, no runtime dependency, acceptable to customers.

4.4 Classifier

Rule-based, hand-tuned from G0 findings. No machine learning until three design partners have produced real traffic. Rules are debuggable and defensible on a call, which matters more than marginal accuracy at this stage — every finding will be challenged by the person who owns the workload.

Emits agent candidates with a confidence score. Confidence below threshold produces a candidate for review, never a register entry (SEC-17).

4.5 Attributor

Resolves principal → resource tags → team → human. This converts "something was detected" into a ticket someone can act on.

Failure mode

A finding with no owner is noise, and noise gets the tool uninstalled. Attribution deserves disproportionate investment relative to how unglamorous it is. If tag hygiene is poor enough that attribution fails, the product is a curiosity rather than a control.

4.6 Baseline and drift

Per-agent rolling baseline: tool set, call volume p50/p95, endpoints reached, active hours. Departures raise a drift finding. This is the Register's detection capability, and it is the honest home of any claim about detecting compromised or misbehaving agents.

§ 05

Phase B — The Checkpoint

Specified in full in the companion production development specification. Summarised here only for how it relates to the Register.

An inline gateway that intercepts consequential agent actions. For each, it verifies the calling agent's signed credential and delegation chain, evaluates the proposed action against deterministic policy, and returns allow, deny, or hold-for-human. Every decision produces a signed receipt. No LLM sits in the decision path. Unknown actions and evaluator errors fail closed.

Dependency on the Register

The Checkpoint's issuers, agents, agent_keys, and delegations tables are populated manually in the companion spec. With the Register, onboarding changes from "enumerate all 40 of your agents" to "review this list and grant imprimatur to the ones you recognise." That is the difference between a pilot that stalls in week one and a pilot that starts.

The hardest requirement in the entire project

SEC-03 requires that the downstream system reject direct traffic that bypasses the Checkpoint. This obliges the customer to reconfigure network paths and credentials so the target system accepts only gateway-originated traffic.

Without it, an agent simply calls the target API directly and Custos becomes a suggestion box. This is a harder ask than anything technical in the project, it is the make-or-break of the enforcement value proposition, and it must be raised in the first pilot conversation rather than discovered during integration.

Availability cost, unpriced

Readiness fails closed when safe enforcement is not possible. Correct security posture; it also means a Custos outage halts the customer's agent workflow. At a 99.5% pilot target that is roughly 3.6 hours per month. No customer has agreed to that yet, and the number belongs in the pilot agreement rather than in a footnote.

Hard scope boundary

No industrial equipment, radiation systems, safety interlocks, medical treatment processes, or autonomous movement of funds. Reversible drafts requiring human approval only. This boundary is not negotiable for a pilot logo, however attractive.

The unsanctioned set — agents in discovered with no imprimatur — is the recurring value delivery. It regenerates on every scan, which is what makes this a subscription rather than an audit engagement.

§ 07

Security invariants

SEC-01 through SEC-15 are specified in the companion production document and are carried forward unchanged. The Register adds three. All are testable and none are relaxable for a feature request.

SEC-16
Discovery is read-only. The collector's credential grants no write permission to any customer resource, and the collector contains no code path that mutates customer infrastructure.
SEC-17
Discovered records confer no authority. A discovered agent cannot execute through the Checkpoint until an operator explicitly grants imprimatur. Discovery populates the register; it never authorises. Without this, traffic that imitates the agent signature would auto-provision itself a credential.
SEC-18
Metadata only. Identities, endpoints, byte counts, timings and protocol fingerprints leave the customer account. Prompts, completions, and payload bodies never do, under any configuration.

On the surveillance question

A tool that inventories every agent and its credentials is reconnaissance-shaped. In practice the uplift to an attacker is near zero, because it requires read credentials they would already have to hold. Two constraints keep it that way: the collector cannot be pointed at an environment its operator lacks legitimate access to, and SEC-18 ensures the data collected describes software rather than the people using it. The metadata-only constraint is what keeps the ethical position defensible — do not trade it away for a feature.

§ 08

Build sequence

Gates, not calendar dates. Durations assume two engineers full time, or one engineer at roughly double.

A0Prove the signal2 weeks

Test environment, flow logs only, hand analysis. Gate G0 in §4.1. Exit: the burst signature separates agents from chatbots, or the fallback is chosen and the pitch revised.

A1Scanner3 weeks

Collector, rule classifier, attribution, reach mapping, static HTML report. No database, no auth, no UI, no multi-tenancy. Exit: a report run against a real environment that surprises the person who owns it.

A2Register6–8 weeks

Persistent store, console, sanction workflow, auth and tenant isolation, scheduled re-scans, Slack and SIEM delivery. Exit: three organisations scanning repeatedly without being prompted.

A3Drift4–6 weeks

Baselining and departure alerts (§4.6). SOC 2 Type I evidence collection begins in parallel — it needs three months of observation and gates the first enterprise deal, not the product. Exit: first paid contract.

B0–B7CheckpointCompanion spec

Shadow mode first — observe proposed actions, evaluate policy, record decisions, execute nothing. Shadow requires almost none of the key management and execution machinery, so it validates demand months before enforcement is safe to ship. Do not build beyond shadow until a paying Register customer asks for it.

§ 09

Commercial plan

Entry motion

Free read-only scan of one non-production account. Non-production is the unlock: it clears a platform lead's approval bar without a security review. The report creates the demand for a production scan, and the production scan creates the demand for continuous monitoring.

Pricing

Per agent under management, tiered. Revenue scales with the growth of the problem rather than with data volume. Early pilots deliberately underpriced at $500–2,500/month: the objective is the word paying, not margin. Enterprise contracts land at $50–150k once the Checkpoint enters scope.

Target profile

80–400 engineers. Series B/C. AWS. Agents adopted bottom-up rather than through a governance programme. No dedicated AI platform team — if one exists, that team is already the product. Skip AI-native startups; at thirty people they know exactly what is running.

Non-code blockers on the first sale

  • Data flow diagram — what leaves the account, where it goes, who can read it
  • Pre-written security questionnaire response
  • Mutual NDA and a simple MSA
  • Public collector repository
  • Cyber liability insurance

The sentence the company is built to be able to say

We scanned N companies. Every one had AI agents their security team had never registered — M of them holding write credentials to production.

§ 12

Not building

Recorded because the pull toward each is strong, and every one of them is a way to avoid the conversation that actually determines whether this works.

  • Multi-tenancy, RBAC, and SSO before a paying customer
  • Key management, KMS integration, signing infrastructure — Checkpoint only
  • Issuer, delegation, and session models — Checkpoint only
  • Execution leases, outbox workers, reconciliation — Checkpoint only
  • Policy authoring UI, simulation, staged rollout
  • Internet-wide agent scanning. Not technically possible without a privileged vantage point, and it inherits the entire civil-liberties objection the in-account model avoids. Cross-customer signal is built from the union of consenting environments, one customer at a time.
  • Machine-learned classification before three design partners have produced real traffic
  • Anything a customer has not asked for by name
